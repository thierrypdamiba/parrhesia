# Docket — final build plan (synthesized 2026-09-03, ~22:00 UTC)

**One line:** a letter-writing workspace bound to one live Federal Register proposed rule, where a person and their agent co-write a public comment; every quoted provision is verified by the page against the rule text it served (a paraphrase is refused with the three nearest real passages), co-signers sign under their own ChatGPT identity, and only a person files.

**Who reads this:** the builder pastes section 6 into Codex in order; a judge reads sections 1, 2, 7 and 8. Everything marked *VERIFIED* was checked live today (2026-09-03) by the planning agents and re-checked by the synthesizer; everything marked *UNVERIFIED* is resolved by Prompt 0 on the hosted runtime before any product code is written.

## 1. Decision and why it wins

**Ship Docket. Fallback: Slack Water (section 11).**

Docket scored highest on the simulated judge panel (33.0 average vs 30.0 for Slack Water; full board in section 12). The red team's verdict was unanimous: *ship the concept, cut the spec, fix four correctness bugs before Codex starts*. All four are fixed below (nearest-passage off-by-one; D1 batch guard that did not abort on stale writes; host-mode misdetection in the ChatGPT browser; hold-to-accept overclaimed as a human proof). Every overclaim the red team flagged is removed from the pitch, Devpost text and on-page copy.

### Per criterion, against the landscape (~495 catalogued entrants)

**WebMCP Leverage (first tie-breaker).** Eight imperative tools registered on the top-level page, each with `title`, JSON Schema (`additionalProperties:false`, enums, `maxLength`, patterns), explicit `readOnlyHint` and `untrustedContentHint` with the reason printed, bounded outputs (1.8K / 4.5K measured budgets), and `{error, hint}` state-aware errors. The tool list is a printed state machine (unbound → bound → closed; sign-in adds `draft_my_impact`; first accepted claim adds `propose_edit`; `open_rule` removes itself), rendered from `getTools()` on `toolchange` in Chrome and from page state with in-execute gating in ChatGPT's browser (both modes honest, both printed on the rail). The distinctive mechanics — a page-side verifier the agent must satisfy (`ANCHOR_NOT_FOUND` with nearest passages, `ANCHOR_NOT_READ` with the exact `read_rule` call), revision-bound proposals with `changed_since` attribution, identity bound to the sign-in session with **no name field in any schema**, and a tool (`ask_person_to_file`) that exists to teach the agent the boundary — are each rare in the landscape and absent as a combination. Evals ship in the webmcp-evals format with a deterministic smoke run and an HTTP walkthrough.

**Execution.** Editorial document design (paper/ink, serif letter text, mono provenance), a real split-pane workspace over 44,458 characters of real rule text with page gutters, a judge path (`?judge=1`) that is deterministic because the seed uses a shipped text snapshot, and a public read-only page. The scope cut (section 10) removes everything not on the 15-second hook or the judge path so half-built drawers do not appear.

**Potential Impact.** 191 proposed rules are open for comment today (Federal Register API, VERIFIED). Under the APA an agency must respond to significant comments in the final rule; comments that identify a provision and ask for a specific change are the ones that get answered. Most comments on regulations.gov are general sentiment; Docket makes the provision-specific form the only form the page will export, and it is built to make comments *harder* to fake, not easier: one letter per group, every quote verified, every signer authenticated with the time they signed, impact statements bound to the signer's own session, filing human-only, agent assistance disclosed in the export.

**Creativity & Ambition.** Zero of ~495 catalogued entrants touch rulemaking, civic comment, petitions or dockets (grep of the landscape for regulat/rulemak/docket/civic/petition/comment: none). The parts are borrowed and credited — revision-bound proposals like Rehearse, a printed tool state machine like Mace/Tendero/Decision Passport, refusal-with-suggestions like Counterask, several people each with their own agent like UNSAID/Patiently — but no entry combines verification of the agent's output against a live source the page itself served with multi-human authenticated identity over a real deadline.

### Why not the runner-up
Slack Water (float-plan desk over four NOAA products) is an excellent second: all data keyless and verified, a deterministic solver, phased tools, a shore-contact page. It lost on Impact (NOAA-adjacent to the El Neenyo bar; a paddler audience is smaller and the "shore contact" record is less consequential than a filed federal comment), on Creativity (Eddy, another float-plan concept, sits right beside it in the same panel), and on build weight (a three-row SVG instrument with drag handles is the heaviest UI in either spec). It remains the fallback because its critical path shares nothing with Docket's riskiest dependency (Sites identity headers on fetch).

## 2. Product spec

### 2.1 Pitch (judge-facing, honest)
Docket binds a letter to one live Federal Register proposed rule. A person's agent searches the open rules, attaches one, reads the rule text through the page (`read_rule`), and proposes claim cards: a verbatim quote, a position (support/oppose/modify), an assertion, and a requested change. The page normalizes whitespace and quotes and requires the quote to be an exact substring of the rule text it fetched; a quote that is not in the rule is refused with `ANCHOR_NOT_FOUND` and the three nearest passages (offsets and Federal Register page numbers); a quote the agent did not read through `read_rule` in this session is refused with `ANCHOR_NOT_READ` and the exact call that would show it. Nothing the agent proposes applies until a person presses and holds Accept; people type into any card directly, and a stale agent proposal fails naming the claim and field the person changed. Co-signers open a share link, sign in with ChatGPT, and their own agent can draft an impact statement only for the session's identity (`draft_my_impact` has no name field). No accept, delete, sign or file tool exists; `ask_person_to_file` always returns `needs_human` with the regulations.gov link. Docket never files.

**Lines deliberately not said** (red-team removals): "read_rule is the agent's only perception channel" (the rule pane renders the full text into the DOM); "ChatGPT cannot fabricate a quote here" (true for the quote field only; assertion/requested change/evidence are free text and labelled as such); "a host that clicks buttons cannot accept" (the held gesture raises the cost of automated clicking, it is not proof of a human — the real guarantee is that no accept tool exists); "agencies must answer" (agencies must respond to significant comments in the final rule).

### 2.3 States
- **Unbound:** rail shows `find_open_rules`, `open_rule`, `get_letter`.
- **Bound, open:** `find_open_rules`, `read_rule`, `propose_claim`, `get_letter`, `ask_person_to_file`; + `propose_edit` once ≥1 accepted claim; + `draft_my_impact` when signed in. `open_rule` absent: "letter is bound to 2026-17902".
- **Bound, closed** (`comments_close_on` < today in America/New_York): grey header "Comments closed 2026-11-02"; `propose_*` and `draft_my_impact` absent with reason "comment period closed 2026-11-02"; reading, export and history still work; link "Start a new letter on an open rule".
- **Rule fetch failed:** header "Could not load rule text from federalregister.gov (HTTP 404/timeout) — retry"; `open_rule` returns `RULE_UNAVAILABLE` with `html_url`.
- **Stale/conflict:** proposal cards say exactly what changed; tools return `STALE_REVISION` with `changed_since`.
- **Empty:** "No open rules match "zzz". Try fewer words."; "No claims yet. Your agent can propose one after reading the rule; or add one by hand."; no signers.
- **Host mode:** rail badge "Chrome: live toolchange" or "ChatGPT browser: all tools registered; gates enforced in execute (rail shows what would succeed now)" or "No WebMCP host detected; the page works by hand."

### 2.4 The Tool Rail
A 40 px monospace strip under the top bar, always visible: "Agent can call now: find_open_rules · read_rule · propose_claim · get_letter · ask_person_to_file" and "Not now: open_rule (letter is bound to 2026-17902) · propose_edit (no accepted claim yet) · draft_my_impact (sign in with ChatGPT to draft for yourself)"; mode badge; a dot that pulses while a tool executes; the last call line "read_rule({query:"30 days"}) → 3 passages (212 ms)".

### 2.5 "How agents use this site" (on page, id="agents"; README carries the same text from one source string)
(a) "This page registers tools with `document.modelContext.registerTool` (`navigator.modelContext` fallback). `read_rule` is the only source of quotes the page accepts: every anchor records the `read_rule` call and offsets that produced it, so a reader can click from a claim to the passage. The page verifies every quote against the same text it served; a person accepts, signs and files." (b) Tool table generated from code (name, title, purpose, readOnlyHint, untrustedContentHint with reason, appears when, key errors). (c) "What tools cannot do": accept or reject a proposal (a held gesture on the page; a click does nothing), delete claims, sign or add a signer, write an impact statement for anyone but the signed-in person (no name field exists in any schema), change the bound rule (`open_rule` unregisters itself), file on regulations.gov (`ask_person_to_file` always returns `needs_human`), cite text that is not in the rule (`ANCHOR_NOT_FOUND`) or that it has not read here (`ANCHOR_NOT_READ` — a page-side grounding discipline, not a security boundary; the server verifies substring only), propose after comments close. (d) Host notes: ChatGPT's in-app browser supports imperative top-level tools only; in that host all eight tools are registered at load and gated inside execute; Chrome shows live registration diffs; the held gesture exists because a host may click page buttons (webmcp issue #288, cited once). (e) "Try it": the judge link and the sample prompt.

### 2.6 What each party can do
**Human by hand:** pick and attach a rule, type or edit any claim field, add a claim by hand (verified the same way), delete (held), accept/reject (held), undo last change (held), add self as signer, write and sign own impact (held), set own public display name, export, share links, open regulations.gov and file.
**Agent:** search open rules, attach a rule (once), read the rule through the page, propose claims and edits bound to the current revision, draft an impact statement for the signed-in person only, read the letter state and checklist, learn that filing is human-only.
**Agent structurally cannot:** accept, reject, delete, sign, add or name a signer, write anyone else's impact, change the bound rule, file, or cite text not in the rule.
**Seeing each other:** the page polls `GET /api/letters/{id}/state?rev=` every 4 s (`{unchanged:true}` or state without rule text); every agent tool call renders immediately; toasts name the actor; attribution stamps `agent-of:<name>` vs `<name>`; the rule pane shades what the agent read; the revision counter ticks; a second participant sees changes within 4 s.

### 4.4 Revision, concurrency, identity, links, limits
- **rev_hash** = hex sha256 (crypto.subtle) of canonical JSON `{document_number, claims:[{id,ord,quote,anchor_start,anchor_end,page,anchor_status,position,assertion,requested_change,evidence}] sorted by ord then id, signers:[{user_id,display_name,impact_text,signed_at}] sorted by user_id}` with keys in exactly that order; `base_rev` in tools/API = first 12 hex, compared by prefix; the full hash is shown in the UI provenance.
- **Atomic write:** every content change is one `env.DB.batch([...])` whose FIRST statement is `INSERT INTO revisions(letter_id, rev_no, …) VALUES (?, <current rev_no>+1, …)` — the PK collision on a concurrent write raises an error and D1 rolls the whole batch back (D1 rolls back only on errors; an UPDATE matching 0 rows is not an error, which is why the hash-guarded UPDATE alone was unsafe). Then `UPDATE letters SET rev_no=?, rev_hash=?, updated_at=? WHERE id=? AND rev_no=?`, content writes, activity insert. Pre-check `base_rev` vs current for `STALE_REVISION` with `changed_since` (diff of the snapshot at base_rev vs current, attributed via intervening revisions).
- **Proposal rules:** `propose_*` require `base_rev` == current at proposal time; on accept, kinds `claim` and `impact` apply against the current revision (they add); kind `edit` re-checks the target field still equals its value at base_rev, else marks the proposal `stale` and returns `STALE_PROPOSAL {field, was, now, by}`. Pending cap 5. Accept requires `hold_ms ≥ 700` (labelled in code as a consistency check, not security).
- **Read-range allowlist (page side):** merged intervals from `read_rule` results this page session (reset on reload; nothing pre-covered). `propose_claim`/`propose_edit(quote)` call `POST /verify` first; if found but not covered → `ANCHOR_NOT_READ` with `read_rule({start: anchor.start-200, window: min(1500, len+400)})`. Human-typed quotes skip the allowlist, never the verifier.
- **Identity:** Worker derives `user_id = hex(sha256(lower(email)))` (or a user-id header if Prompt 0 shows one) and `display_name = full-name header || 'Signer'`; sanitized to ≤40 chars, single line, `[A-Za-z0-9 .'-]`. The email is never stored, returned, or shown. Fallback when headers are navigation-only: on any document request carrying the headers the Worker sets an httpOnly SameSite=Lax cookie `docket_session = HMAC(user_id, display_name, exp)` and every `/api` route accepts headers or that cookie. Sign-in return path: `/api/signin?return_to=/l/…` sets a `docket_return` cookie and 302s to `/signin-with-chatgpt`; the SPA root reads `/api/me` and redirects when the cookie is present. Anonymous visitors get an httpOnly `docket_owner` cookie; letters store `owner_token_hash`. Edit permission: owner OR share_code path. Signer rights: only the signed-in user for their own row; no API body ever carries a name or user id (unknown keys → `400 UNKNOWN_FIELD` naming the key).
- **Links:** `/l/{share_code}` (22-char base32, editable, tools registered); `/r/{public_token}` (read-only, `get_letter` + `read_rule` only, no writes). Judge fork per 2.2 item 9; judge forks have their own rate bucket (30/hour/IP); letters 60/hour/IP; proposals 120/hour; binds 60/hour; reads 600/hour. Nothing is pruned before 2026-10-01.
- **Text delivery:** rule text served from `GET /api/rules/:document_number/text` (ETag = text_sha256, `Cache-Control: public, max-age=86400, immutable`); letter state never embeds the text.
- **Undo:** "Undo last change" writes a new revision equal to snapshot N−1. All text stored as-is and rendered as text nodes.

## 8. Devpost

**Title:** Docket

**Tagline:** Co-write a public comment on a live federal rule with your agent. Every quote is verified against the rule; every signer is a person; a person files.

**Description:**

*Why WebMCP fits.* A public comment carries weight when it quotes the specific provision and asks for a specific change. Docket binds a letter to one live Federal Register proposed rule (191 are open for comment today) and exposes eight page tools. `read_rule` is the only source of quotes the page accepts; `propose_claim` requires the quote to be an exact normalized substring of the text the page served: a paraphrase is refused with `ANCHOR_NOT_FOUND` plus the three nearest passages with offsets and page numbers, and a quote the agent never read through the page is refused with `ANCHOR_NOT_READ` and the exact `read_rule` call to make. The tool list is a state machine the page prints: `open_rule` unregisters itself after binding, `read_rule` and `propose_claim` appear once a rule is attached, `propose_edit` after the first accepted claim, `draft_my_impact` only when the viewer is signed in with ChatGPT, and every writing tool disappears the day comments close. No accept, delete, sign or file tool exists; `ask_person_to_file` always returns `needs_human`. These guarantees live in the page's tools, not in a prompt.

*Better user experience.* Person and agent work in one document: the agent proposes claim cards bound to the letter's revision; the person types into any field directly, and a stale agent proposal fails naming the exact claim and field that changed. Accept is a held gesture on the page. Anchored quotes light up in the rule pane with page numbers; what the agent read is shaded; the deadline countdown is in the header and in every `get_letter` result. Co-signers open a share link, sign in with ChatGPT, and their own agent can draft only their impact statement (no name field exists in any schema). Export is plain text with page-cited quotes, an agent-assistance disclosure, and a human-only link to regulations.gov.

*What people and agents can do together that was hard before.* A small group can produce, in one sitting, a provision-specific multi-signer comment on a rule that closes in weeks: the agent finds the rule and reads 44,000 characters of Federal Register text so the person does not have to, proposes claims that are provably quoted, and drafts each signer's impact statement under that signer's own identity; the people decide, edit, sign and file. Under the APA an agency must respond to significant comments in the final rule; comments that identify a provision and ask for a specific change are the ones that get answered, and most comments on regulations.gov are general sentiment. Docket makes the provision-specific form the only form the page will export.

*Why this is not a comment factory.* One letter per group; every quote verified; every signer authenticated by Sign in with ChatGPT with the time they signed; impact statements bound to the signer's own session; `ask_person_to_file` always needs a human; assertion, requested change and evidence are labelled as the claimant's own words, not verified text; the export discloses agent assistance.

*What is new.* The parts have precedents we credit — revision-bound proposals like Rehearse, a printed tool state machine like Mace, refusals with suggestions like Counterask — and what no entry does is verify the agent's output against a live source the page itself served, with several authenticated people each bringing their own agent to one document, over a real deadline.

*How it is implemented.* Vite + React on ChatGPT Sites (Cloudflare Workers runtime) with D1 for letters, claims, proposals, signers, revisions and activity. Tools are registered imperatively on the top-level page with `document.modelContext.registerTool` (`navigator.modelContext` fallback), each with title, JSON Schema (`additionalProperties:false`, enums, maxLength), `readOnlyHint` and `untrustedContentHint` with reasons, bounded results (1.8K; `read_rule` 4.5K), and `{error, hint}` state-aware errors. In Chrome the tool set is diffed against `getTools()` with per-tool AbortControllers and the on-page rail re-renders on `toolchange`; in ChatGPT's browser all eight tools are registered at load and every gate is enforced inside execute (host mode: <measured in Prompt 7>). The Worker fetches Federal Register JSON and raw text, normalizes whitespace and quotes deterministically (norm-1), stores page and paragraph offsets, and verifies anchors by exact substring with a Jaccard nearest-passage search for refusals. Revision hash = sha256 of canonical letter JSON; every write is one D1 batch that inserts the next revision row first so a concurrent write aborts the batch. Identity is derived from the Sign in with ChatGPT headers (sha256 of the email; the email is never stored or shown). Evals ship in webmcp-evals format with a deterministic smoke run and an HTTP walkthrough. Rule text for the judge letter is a snapshot from 2026-09-03; live letters fetch the current text. Docket never submits comments; regulations.gov is a human link-out, and 7% of open rules have no regulations.gov form, in which case Docket links to the rule's ADDRESSES section.

## 9. Risks and mitigations

1. **ChatGPT's browser may snapshot the tool list** (unverified mid-conversation refresh; docs only say tools 'belong to the page'). Prompt 0 measures it; in that host all eight tools register at load with gates in execute; the hook does not depend on a tool appearing mid-turn; README states the mode per host.
2. **Identity headers may ride only on navigations, not fetch().** Prompt 0 measures it; the HMAC session-cookie fallback and the `/api/signin?return_to` cookie make the co-signer flow independent of the answer. If hosted sign-in fails entirely, the single-author path covers the whole tool demo and the video shows the builder's own sign-in only.
3. **Host may click page buttons (webmcp #288).** Held gesture with `isTrusted`, no click path, server hold check — presented as raising the cost of automated clicking, never as proof of a human; the real guarantee is the absence of an accept tool. Cited once.
4. **Stale writes committing silently.** Fixed by inserting the `revisions` row first (PK collision aborts the D1 batch). Concurrency test in the walkthrough.
5. **Normalizer drift.** Fixture-pinned numbers regenerated by the shipped Python script; trimmed nearest candidates; quote-side dash/§/footnote mapping; retry + XML fallback; `read_rule` serves the verifier's own string.
6. **federalregister.gov blocking Workers egress** (HTML routes 302 to unblock.federalregister.gov for non-browsers; JSON/raw answered curl today). Prompt 0/7 measure from the Worker; fallback to client-side JSON (CORS *) with Worker text; the judge path runs on the shipped snapshot regardless.
7. **Wrong rule bound in demos** (`bicycle` ranks 2026-15406 first). Sample prompts name the document number; the search boosts document-number/title matches; README names the sibling rule.
8. **Non-deterministic refusal beat.** The demo forces it with an explicit 'without checking it first' instruction; the seeded unverified claim and the judge box are the deterministic fallbacks; the stale beat is the human-driven stale card, not the agent's call order.
9. **Live rule changes during judging** (extension/withdrawal). Closed state is designed and printed; the judge letter is pinned to the snapshot; `find_open_rules` shows real alternatives.
10. **Rate limits at judging.** Judge letters are reused per visitor and have their own bucket; nothing pruned before 2026-10-01; 15-minute FR cache with stale fallback.
11. **Scope.** The cut in section 10 keeps only the hook and the judge path in core; P8–P10 are ordered after the first deploy so nothing half-built is judged.
12. **Text-on-text video.** Open on the bound letter, refusal by 0:12, green chip and held accept by 0:18; second-signer beat is conditional on P8.
13. **Sites audience/public publishing.** Tested in Prompt 0 before product code; the code targets the Workers runtime so a Cloudflare host with the same D1 schema is one config change if public publishing is unavailable.

## 11. Fallback concept (one page): Slack Water

**What it is.** A float-plan desk where a paddler and their agent turn four live NOAA products — CO-OPS tide predictions, CO-OPS current predictions, NDBC buoy observations, NWS Coastal Waters Forecast and marine alerts — into one human-pinned launch window and a published float plan a shore contact opens by link and re-checks against live conditions (GO / NO-GO / UNKNOWN). All data keyless public NOAA, verified 2026-09-03; predictions deterministic, so `?judge=1` renders the same curve and windows for every judge.

**Screens.** Landing with a live mini-curve; the desk (`/plan/{id}`): station strip with provenance chips; a three-row SVG Instrument on one 36-hour axis (tide curve from the reference station with hi/lo from the launch station, current ribbon for a chosen station/bin with slack markers and ±limit lines, hourly NWS wind bars with hatched alert spans); bands for candidate (green), proposed (amber, reason chips) and pinned (teal, stamp) windows with drag handles; a conditions card (buoy with FRESH/STALE age; CWF text in an 'untrusted' quote style with product id and issue time); a plan rail (site, limit sliders that compile into tool schema maximums with a policy hash, windows, legs ≤8, crew/overdue/notes, hold-to-publish, share card); an agent section rendered from `getTools()`/`toolchange` with reasons and three probe buttons; `/p/{token}` shore page with a held 'Reported back'; `/me`.

**Tools (10).** Always: `get_plan_state` (read), `find_stations` (read; returns a question card when several current stations/bins are in range), `set_launch_site` (write; revision-bound; `site_locked` after a pin). After candidates this session: `propose_window` (may only reference returned candidate ids; refusal ladder unknown_ref → outside_candidate → violates_limits with nearest compliant → inside_alert → locked_by_human → stale). While a human has pinned: `add_leg`, `set_crew_and_notes`, `request_publish` (always `needs_human`). No pin/unpin/drag/publish/report tool; 700 ms held gestures for those.

**Data (verified).** CO-OPS `datagetter` (`predictions` interval=30 only for reference stations, type R; subordinates hilo only; `currents_predictions` MAX_SLACK and interval=30 with sine interpolation for subordinate current stations; `water_level` date=latest), CORS *; mdapi station lists bundled at build (~130 KB gz); NDBC `realtime2/<id>.txt` + `.spec` (no CORS → Worker route, m/s→kt, m→ft, stale >180 min = UNKNOWN); NWS `/points`, `/gridpoints/…/forecast/hourly`, `/zones?type=marine&point=` (probe 8 compass offsets at 1 and 3 nm), `/alerts/active?zone=`, `/products/types/CWF/locations/<office>` + `/products/{id}` (split on `\n$$\n`; synopsis by /ynopsis/), User-Agent required (403 when empty), allowlisted Worker proxy; sunrise/sunset computed in-page.
